# Contributing

Thanks for looking at Laterna Web. This page covers how to run, build and test the client and the
rules the code base holds itself to. The reasons behind the design are in
[`docs/design/`](docs/design/README.md); reading the note for the area you touch saves time.

## Setup

You need:

- [Node.js](https://nodejs.org/) 22 or later and [pnpm](https://pnpm.io/) 11 (`corepack enable`
  picks the version pinned in `package.json`);
- a Laterna server to talk to. Clone the
  [server repository](https://github.com/laterna-project/laterna) and start it with `task dev`
  (it needs Go, go-task and FFmpeg; see its own CONTRIBUTING.md). It serves on
  http://localhost:8096 with its data in `.dev/`.

Then:

```sh
pnpm install
pnpm dev
```

The app opens on http://localhost:5173. Vite proxies the API and the server's byte routes
(images, streams, fonts, books, downloads, logs, backups, the OpenID Connect callback, metrics)
to `LATERNA_URL` (default http://localhost:8096), so the app and the API share one origin.

To try passkeys, OpenID Connect or the device login page in development, set the server's public
address to http://localhost:5173 (Administration › Authentication).

## Commands

| Command | What it does |
|---|---|
| `pnpm dev` | Run the app on http://localhost:5173 against `LATERNA_URL`. |
| `pnpm check` | Everything that must pass before a change is done; CI runs the same. |
| `pnpm gen` | Regenerate the API client (`src/gen`) and copy the server's English and French text catalogs (`src/i18n/server`), from the server version pinned in `package.json`. |
| `pnpm gen:check` | Fail if `src/gen` or those catalogs differ from that version. |
| `pnpm test`, `pnpm lint`, `pnpm fmt`, `pnpm typecheck`, `pnpm build` | The usual. |
| `pnpm samples [movies\|shows\|anime\|music\|books\|photos]` | Build the free sample libraries in `~/laterna-samples` (`LATERNA_SAMPLES` for another folder). About 5 GB; needs FFmpeg and, outside Windows, `bsdtar` (`libarchive-tools` on Debian and Ubuntu). |
| `pnpm seed` | Set up a new server through the API: administrator, a test account, a kid profile, the sample libraries, a scan. Credentials go to `.dev/seed.json` (not committed). |
| `pnpm seed:activity` | Simulate some use of the main profile, so that the home rows fill up. |
| `pnpm party:bot <code>` | A second member for a watch party: the test account joins, gets ready when the group waits, says hello and reacts. Ctrl+C leaves. |

To start from a new server: stop it, delete the server's `.dev` folder, start it again, then run
`pnpm seed`.

### Working against an unreleased server

`pnpm gen` reads the server version pinned in `package.json` (`laternaServer`) from GitHub. While
a change spans both repositories, point it at a local checkout instead:

```sh
LATERNA_SOURCE=../laterna pnpm gen
```

Before merging, the server change must be released and the pin moved to that version:
`pnpm gen:check` (and CI) always compare with the pinned version.

## Rules of the code base

**Only what the server does.** Before building a screen, check that its RPCs exist in the
contract. The client never fakes a feature the API does not offer.

**The contract comes from the server.** `src/gen` is generated by buf and `protoc-gen-es`, is
committed, and is never edited by hand. Use it directly with connect-query:
`useQuery(ServerService.method.getServerInfo, {})`. After a change made here, refetch whole
services with `useInvalidate`; the server's event stream does the rest.

**Accessibility.** WCAG 2.2 AA. Every screen has a `main` and an `h1`. In development,
`await laternaAudit()` in the browser console runs axe-core on the current page; a screen is done
when the audit is clean and everything works with the keyboard. See
[docs/design/accessibility.md](docs/design/accessibility.md).

**No interface text in the code.** Every text is a key, in `src/i18n/locales/en.json` (the
reference) **and** in the catalog of every language offered; a test checks they match. In a
component use `useTranslation()`, elsewhere `i18n.t()`. Dates, numbers and lists go through
`locale()`, `num()` and `list()`. Texts and errors from the server arrive as keys and parameters:
display them with `serverText`, `named` and `errorMessage`. See
[docs/design/i18n.md](docs/design/i18n.md).

**Themes.** Colors, generic radii, density and the text font come from the profile's theme on
the server; the device's style keeps layout, headings, shapes and universe colors. Components only
use the tokens of the contract (`src/theme/contract.ts`) through `var(--...)`: no color is written
outside the theme files, and a test checks it. Anything a theme should be able to target carries a
`data-ui` hook from `src/theme/hooks.ts`; the list, the code and the
[authors' guide](docs/themes.md) must agree, and a test checks that too. See
[docs/design/themes.md](docs/design/themes.md).

**Sample media.** Only works that are free in France, where the project started: public domain,
CC0, CC BY, CC BY-SA, never NC or ND. Each is credited in
[`devtools/samples/ATTRIBUTIONS.md`](devtools/samples/ATTRIBUTIONS.md). The server only reads NFO
files and local images, so the samples script writes them. See
[docs/design/sample-media.md](docs/design/sample-media.md).

**Tests.** Tests live next to the code (`*.test.ts`, `*.test.tsx`). They run in Node by default;
a component test starts with `// @vitest-environment jsdom`. Pure logic (formatting, sync, queue,
layout) is kept out of components so that it can be tested without a browser. Against the server,
use a real server, never a fake one.

**Dependencies.** None is added without a written reason, and there is one way of doing each
thing.

**Style.** Comments explain why, in plain English. Identifiers are English. Biome formats and
lints; `pnpm fmt` fixes what it can.

## Layout

| Folder | What it holds |
|---|---|
| `src/gen` | The generated API client. |
| `src/api` | Transport, session, errors, server texts, shared queries, the event stream. |
| `src/app` | Router, page focus and tab titles, the accessibility audit. |
| `src/routes` | One route per file (TanStack Router); `_app` is the signed-in app. |
| `src/features` | Screens and their parts, by area (catalog, home, music, books, photos, lists, account, admin...). |
| `src/player`, `src/music`, `src/books`, `src/photos`, `src/party` | The video player, the music player, the readers, the photo viewer, watch parties. |
| `src/theme` | The token contract, the built-in styles, server themes, imported themes, `data-ui` hooks. |
| `src/i18n` | Languages, the interface catalogs and the server's text catalogs. |
| `src/ui` | Base components, without business logic. |
| `devtools` | The sample libraries and seed scripts, and the Vite plugins of the build. |
| `scripts` | Code generation. |

## Branches

The project follows git-flow. For a contribution, only two branches matter:

- **`develop`** is the default branch and the one to start from. It holds the next release.
- **`main`** only holds released versions. Do not open pull requests against it.

Name your branch after what it does: `feature/...`, `fix/...`, `docs/...`, `ci/...`. Maintainers
handle `release/*` and `hotfix/*`; the whole model, versions and the release steps are in
[docs/releasing.md](docs/releasing.md).

## Submitting a change

1. Open an issue first for anything that changes the design, or needs something from the server.
2. Branch from `develop`, keep the change focused, and update the design note it contradicts or
   extends.
3. Run `pnpm check`, and check the screens you touched in the browser, with the keyboard and
   `laternaAudit()`.
4. Open a pull request against `develop`. It is squashed when merged, and its title becomes the
   commit subject: write it in English, in the imperative, with a
   [gitmoji](https://gitmoji.dev/) in front (`✨ Add ...`, `🐛 Fix ...`, `♻️ Refactor ...`).
   Release notes are built from these subjects.

Everyone taking part is expected to follow the [code of conduct](CODE_OF_CONDUCT.md).
